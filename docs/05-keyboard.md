# 5. PS/2 keyboard driver

Files: `src/keyboard.c`, `src/keyboard.h`.

The keyboard is the kernel's only input device. The driver decodes scancode
set 1 (the PC/AT default, US layout), tracks Shift and Caps Lock, and puts
ASCII bytes into a 256-byte ring buffer that the shell reads. Decoding happens
in the IRQ1 handler; the shell blocks with `hlt` when the buffer is empty.

## 5.1 Hardware interface

| Port | Name | Use |
|---|---|---|
| `0x60` | data | read scancodes / write controller data |
| `0x64` | status (read) / command (write) | bit 0 = output buffer full, bit 1 = input buffer full |

The 8042-compatible controller raises IRQ1 when a byte is available. Reading
port `0x60` acknowledges the byte and lets the controller deliver the next one.
The keyboard sends one byte per make (press) or break (release) event, plus a
leading `0xE0` for extended keys.

The driver assumes the firmware has already:

* enabled the keyboard interface,
* enabled scanning,
* selected scancode set 1,
* left the controller's translation enabled.

`keyboard_init` does not send any controller commands. It only drains stale
bytes and registers the IRQ handler. See the caveats at the end.

## 5.2 Scancode set 1 basics

For the main key block:

* a **make code** is the key number, e.g. `0x1E` for `A`;
* a **break code** is the make code with bit 7 set, e.g. `0x9E`;
* `0xE0` prefixes an extended key (arrows, right Ctrl/Alt, keypad Enter, …);
* `0xE1` prefixes the Pause/Break sequence;
* key repeat is generated by the controller as repeated make codes.

The main block is translated with two 128-entry lookup tables:

```c
static const char keymap[128] = {
    [0x02] = '1', [0x03] = '2', ...
    [0x0E] = '\b', [0x0F] = '\t',
    [0x10] = 'q', ...
    [0x1C] = '\n',
    [0x1E] = 'a', ...
    [0x39] = ' ',
};
```

Designated initializers make every unlisted scancode zero, which the decoder
treats as "no character". The shifted table contains only the keys whose
Shift form differs from the unshifted form:

```c
static const char keymap_shift[128] = {
    [0x02] = '!', [0x03] = '@', ...
    [0x1A] = '{', [0x1B] = '}', ...
    [0x35] = '?',
};
```

Letters are handled separately because their shifted form is just uppercase,
which is cheaper than a second table and interacts with Caps Lock.

## 5.3 State

```c
static volatile char buffer[KEYBOARD_BUFFER_SIZE];
static volatile uint16_t buffer_head;
static volatile uint16_t buffer_tail;
static int shift_down;
static int caps_lock;
static int extended;
```

* `buffer`, `head` and `tail` are shared with the shell, so they are
  `volatile` and only touched with interrupts disabled on the reader side.
* `shift_down` tracks either Shift key (left `0x2A`, right `0x36`). It is set
  on make and cleared on break.
* `caps_lock` toggles on each Caps Lock make (`0x3A`); break (`0xBA`) is
  ignored.
* `extended` remembers that the previous byte was `0xE0`.

`shift_down`, `caps_lock` and `extended` are only accessed from the IRQ
handler, so they do not need `volatile` or locking. They would become shared
state if another context ever read them.

## 5.4 The IRQ handler

```c
static void keyboard_irq(void)
{
    uint8_t scancode = inb(KEYBOARD_DATA_PORT);

    if (scancode == 0xE0) {
        extended = 1;
        return;
    }
    if (extended) {
        extended = 0; /* arrows, delete, ... are not used by the shell */
        return;
    }

    int released = scancode & 0x80;
    uint8_t code = scancode & 0x7F;

    if (code == 0x2A || code == 0x36) {
        shift_down = !released;
        return;
    }
    if (code == 0x3A) {
        if (!released)
            caps_lock = !caps_lock;
        return;
    }
    if (released)
        return;

    char c = translate(code);
    if (c != '\0')
        buffer_push(c);
}
```

Step by step:

1. Read the byte from port `0x60`. This also acknowledges it.
2. If it is `0xE0`, set the prefix flag and stop. The *next* byte will be an
   extended key code and is discarded by the next call.
3. If the prefix flag is set, clear it and stop. This intentionally ignores
   the entire extended key space: arrows, Delete, Home/End, Page Up/Down,
   right Ctrl/Alt, keypad Enter, and the `E0` fake-shift sequences. The shell
   has no history or cursor movement.
4. Extract `released` from bit 7 and mask it off to get the 7-bit key number.
5. Left or right Shift: set/clear `shift_down` according to the break bit.
6. Caps Lock: toggle on make only. Repeat make codes (`0x3A` repeated while
   held) would toggle repeatedly; the controller's typematic repeat for Caps
   is not normally enabled, and on QEMU this behaves as expected.
7. Any other break code is ignored.
8. Translate the make code to ASCII and push it if it is not `'\0'`.

Because the handler runs through an interrupt gate, `IF=0` for its duration.
It does one port read and a few branches, so the latency is tiny.

### What happens to Ctrl, Alt and function keys

`0x1D` (Ctrl), `0x38` (Alt), `0x3B`–`0x44` (F1–F10), `0x47`–`0x53` (keypad,
Home, arrows, etc.) are not in `keymap`, so they translate to `'\0'` and are
dropped. Ctrl+letter therefore produces the plain letter, not a control code;
there is no Ctrl-C handling. Alt+key is likewise a plain key.

## 5.5 Translation

```c
static char translate(uint8_t code)
{
    char c = keymap[code];

    if (c == '\0')
        return '\0';

    if (c >= 'a' && c <= 'z') {
        if (shift_down ^ caps_lock)
            c = (char)(c - 'a' + 'A');
        return c;
    }

    if (shift_down) {
        char shifted = keymap_shift[code];
        if (shifted != '\0')
            c = shifted;
    }
    return c;
}
```

The rules:

* Unknown key → `'\0'`.
* Letter → uppercase if exactly one of Shift and Caps Lock is active.
  * neither: lowercase
  * Shift only: uppercase
  * Caps only: uppercase
  * both: lowercase (the XOR cancels)
* Non-letter with Shift → use the shifted table if it has an entry.
* Non-letter without Shift → use the base table.
* If Shift is held but the key has no shifted form, the base character is
  kept (e.g. Shift+Tab stays `'\t'`, Shift+Space stays `' '`).

Enter (`0x1C`) becomes `'\n'`, Backspace (`0x0E`) becomes `'\b'`, Tab (`0x0F`)
becomes `'\t'`. The shell handles `'\n'` and `'\b'` and ignores Tab because it
only accepts bytes in the printable range `' '`..`'~'`.

## 5.6 The ring buffer

```c
#define KEYBOARD_BUFFER_SIZE 256
```

```c
static void buffer_push(char c)
{
    if ((uint16_t)(buffer_head - buffer_tail) >= KEYBOARD_BUFFER_SIZE)
        return; /* full: drop the newest character */
    buffer[buffer_head & (KEYBOARD_BUFFER_SIZE - 1)] = c;
    buffer_head++;
}
```

The buffer uses monotonically increasing 16-bit counters, not wrapped indices:

* `head` is the next write position, advanced only by the IRQ handler.
* `tail` is the next read position, advanced only by the shell.
* The number of bytes stored is `(uint16_t)(head - tail)`.
* The array index is `counter & 255`.

Why the subtraction works across counter wrap: the counters are `uint16_t`, so
they wrap modulo 65536. The buffer size 256 divides 65536 exactly, so the
difference modulo 65536 is always the true occupancy in the range 0..256. When
256 bytes are stored, the difference is 256 and the buffer is considered full.

The buffer is **single-producer/single-consumer**: only the IRQ handler writes
`head`, only the shell writes `tail`, and each side only reads the other's
counter. That makes the lock-free access safe on a single CPU. `volatile`
prevents the compiler from caching the counters in registers across the loop.

When the buffer is full, the **newest** character is dropped. The oldest 256
characters remain and will be processed first. There is no overflow counter,
beep or flow control.

## 5.7 Blocking read

```c
char keyboard_getchar(void)
{
    for (;;) {
        interrupts_disable();
        if (buffer_head != buffer_tail) {
            char c = buffer[buffer_tail & (KEYBOARD_BUFFER_SIZE - 1)];
            buffer_tail++;
            interrupts_enable();
            return c;
        }
        /* STI's shadow guarantees the CPU does not miss a wakeup here. */
        __asm__ volatile("sti; hlt" ::: "memory");
    }
}
```

Step by step:

1. Disable interrupts so the head/tail pair cannot change mid-check.
2. If the buffer is non-empty:
   * read the byte at `tail & 255`,
   * advance `tail`,
   * re-enable interrupts,
   * return the byte.
3. If the buffer is empty, execute `sti; hlt`:
   * `sti` sets `IF`, but the CPU delays recognition until after the next
     instruction. That next instruction is `hlt`.
   * If a key arrives between the check and the `sti`, the interrupt is
     pending; after `sti`, `hlt` still executes, and the pending interrupt
     wakes the CPU immediately. No wakeup is lost.
   * If no key is pending, the CPU sleeps until IRQ1.
4. After the interrupt returns (`iret` restores `IF=1`), the loop repeats and
   finds the byte.

`keyboard_getchar` assumes it is called with interrupts enabled and leaves them
enabled on return. In the shell that is always true; during early boot it is
not called. The `"memory"` clobber prevents the compiler from moving buffer
loads across the inline assembly.

Why not use a normal spinlock? There is one CPU, one producer and one consumer,
and the reader disables interrupts. A lock would add no safety. The only
critical section is the head/tail check and the tail update, which must be
atomic with respect to IRQ1.

## 5.8 Initialization

```c
void keyboard_init(void)
{
    /* Drain anything the firmware left in the controller. */
    while (inb(KEYBOARD_STATUS_PORT) & 0x01)
        (void)inb(KEYBOARD_DATA_PORT);

    irq_register_handler(1, keyboard_irq);
}
```

Status bit 0 means "output buffer full": a byte is waiting in the controller.
Reading `0x60` removes it. The loop discards any bytes the firmware or an
earlier session left behind, so the first shell command does not start with a
stray character.

`irq_register_handler(1, keyboard_irq)` stores the function pointer in
`irq_handlers[1]`. It does **not** unmask IRQ1; that happens at the end of
`kernel_main` with `pic_unmask(1)`.

The drain loop has no iteration cap. If the controller reported "full"
forever (for example because it is absent and the status port floats high), the
loop would hang. On QEMU and normal PCs the bit clears after a bounded number
of reads. A defensive implementation would cap the loop at, say, 64
iterations.

## 5.9 Key repeat

The 8042 generates typematic repeat by sending repeated make codes while a key
is held. The decoder sees each repeat as a fresh press and pushes another
character. There is no software repeat timer, no repeat delay/rate
configuration, and no way to distinguish a repeat from a real second press.
This is exactly what the shell wants for typing.

## 5.10 Caveats and limitations

* **US layout only.** There is no keymap selection, no dead keys, no AltGr and
  no compose sequences. `keymap` and `keymap_shift` are hard-coded.
* **Scancode set 1 only.** The driver never sends `0xF0` to select a set and
  does not decode set 2/3. A keyboard configured for set 2 by firmware would
  produce garbage or no characters.
* **No LED updates.** Caps Lock state is tracked in software but the Caps Lock
  LED is never changed. BIOS-set LEDs may disagree with `caps_lock`.
* **No Ctrl/Alt modifiers.** Ctrl-C, Ctrl-D, Ctrl-L and similar are not
  implemented. Ctrl+letter yields the letter.
* **No extended keys.** Arrows, Delete, Home/End, Page Up/Down, Insert, keypad
  keys and right-side modifiers are discarded. There is no command history.
* **`0xE1` (Pause) is not handled.** The three-byte Pause sequence arrives as
  `E1 1D 45`, then `E1 9D C5`; the driver treats `0x1D` and `0x45` as unknown
  unmapped keys and drops them. No character is produced, so the effect is
  harmless.
* **No mouse.** IRQ12 stays masked.
* **No controller commands.** No self-test, no interface enable, no scan enable,
  no keyboard reset, no buffer-size query.
* **No overflow reporting.** A fast typist can silently lose the newest
  characters beyond 256.
* **One reader.** Calling `keyboard_getchar` from two contexts would race on
  `tail`.
* **IRQ handler trusts the controller.** It reads exactly one byte per IRQ1.
  If a controller asserts IRQ1 for a byte that is not a keyboard scancode
  (e.g. a mouse byte in some configurations), it would be decoded as a key.
  The standard controller routes mouse bytes to IRQ12, so this is not an issue
  here.
